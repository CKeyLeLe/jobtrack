# Architecture decisions

Short record of the main technical choices and their trade-offs.

## 1. Project setup

- **Monorepo** (`backend/`, later `frontend/`): one history, one CI pipeline.
- **Spring Boot 3.5 on Java 21**: widely used LTS stack. Spring Boot 4 exists;
  3.5 was chosen deliberately as the version most teams run today.
- **Configuration through environment variables** with local defaults
  (`${DB_URL:...}`): the same artifact runs locally, in Docker and in production.
- **Tests on H2 (PostgreSQL mode)**: fast and Docker-free. Trade-off: H2 is not
  PostgreSQL, so the schema is also verified against a real PostgreSQL.

## 2. Domain model and schema

- **Flyway owns the schema**, Hibernate only validates it (`ddl-auto=validate`).
  Migrations are versioned, reviewed in Git and replayed identically everywhere.
  A migration is never edited once applied: changes go into a new `V<n>__*.sql`.
- **Package by feature** (`user`, `jobapplication`) rather than by layer: each
  feature keeps its entity, repository, service and controller together.
- **Unidirectional `@ManyToOne` from `JobApplication` to `User`**, `LAZY`.
  `User` has no collection of applications: they are always fetched by query
  (filtered, sorted) and never loaded by accident.
- **Ownership in every query** (`findByIdAndUserId`): a user can never reach
  another user's application, even by guessing an id.
- **Enum stored as text** (`EnumType.STRING`) plus a database `CHECK`
  constraint: readable data, safe reordering, invalid values rejected twice.
- **Emails normalized to lowercase** in the entity so the unique constraint is
  case-insensitive in practice.
- **Entities never leave the service layer**: controllers will use DTOs
  (step 3) to control the API contract and never expose `passwordHash`.
- **No Lombok**: explicit constructors and getters; entities have no public
  no-arg constructor, so required fields cannot be forgotten.
- **Timestamps truncated to microseconds**, the precision PostgreSQL stores,
  so a value returned after an insert equals the value read back later.

## 3. Applications CRUD

- **Three layers, one responsibility each**:
  - *Controller*: HTTP only (routes, status codes, `@Valid`), no business logic.
  - *Service*: business rules and the transaction boundary; knows nothing about HTTP.
  - *Repository*: data access, generated by Spring Data.
- **DTOs as Java records**: `JobApplicationRequest` (input) has no id, owner or
  technical dates, so clients cannot set them; `JobApplicationResponse`
  (output) never exposes the owning user. The API contract can evolve
  independently of the database.
- **Validation at the edge** with Bean Validation on the request DTO, including
  a cross-field rule (`followUpOn` not before `appliedOn`). Invalid requests
  never reach the service.
- **`@Transactional(readOnly = true)` on the service class**, overridden on
  write methods. Updates rely on Hibernate dirty checking: no explicit `save()`.
- **The owner id is a service parameter**: the service is unit-tested with
  Mockito without Spring or a database.
- **Same 404 for "missing" and "not yours"**: does not reveal that another
  user's application exists.
- **`CurrentUserProvider` interface**: controllers do not depend on how the
  user is identified. Step 3 uses a temporary, insecure `X-User-Id` header
  implementation, replaced by JWT in step 6 without touching controllers.
- **REST semantics**: `POST` → 201 + `Location`, `PUT` = full replacement,
  `DELETE` → 204.
- **Test pyramid**: Mockito unit tests (service), `@WebMvcTest` slice tests
  (HTTP contract), one `@SpringBootTest` integration test (full stack on H2).

## 4. Error handling

- **One `@RestControllerAdvice`** (`GlobalExceptionHandler`) translates every
  exception into an HTTP response. Controllers and services never build error
  responses themselves; business exceptions (`NotFoundException`) know nothing
  about HTTP.
- **RFC 7807 Problem Details** (`application/problem+json`): a standard format
  (`type`, `title`, `status`, `detail`, `instance`) supported natively by
  Spring's `ProblemDetail`. Every error has the same shape, so the frontend
  needs a single error interceptor.
- **Extending `ResponseEntityExceptionHandler`** covers framework errors
  (malformed JSON, wrong parameter type, unsupported method, unknown route,
  `ResponseStatusException`) with the same format, for free.
- **Validation errors list each field** (`errors: [{field, message}]`, sorted)
  so a form can show the message under the right input.
- **Cross-field rule as a custom class-level constraint**
  (`@FollowUpNotBeforeApplication`) that attaches the error to `followUpOn`
  instead of the whole object.
- **Catch-all 500 handler**: logs the stack trace, returns a generic message.
  Internal details (SQL, class names) never reach the client.

## 5. Status filter and follow-ups

- **Filter as an optional query parameter** (`?status=INTERVIEW`) on the
  collection, not a separate route: the standard REST way to narrow a list.
  Spring converts the text to the enum; unknown values become a 400.
- **Follow-ups as a dedicated read-only route** (`/follow-ups`): it is a
  business view with its own rule, not just a filter.
- **Business rule**: a follow-up is due when its date is today or earlier
  *and* the application is still active (`APPLIED`, `INTERVIEW`, `OFFER`).
  Rejected or withdrawn applications drop out automatically; their planned
  date is kept as history instead of being erased.
- **Most overdue first** (`followUpOn asc`), since the oldest is the most urgent.
- **Injected `Clock`** instead of `LocalDate.now()`: tests freeze "today" and
  stay deterministic whatever day they run. Known limit: "today" uses the
  server time zone; per-user time zones would need a user setting.
- **Derived queries while readable, JPQL `@Query` beyond**: the follow-up query
  would make an unreadable method name.
- **`id` as a tie-breaker in every sort**: stable ordering between calls.
- **Existing indexes match these queries**: `(user_id, status)` and
  `(user_id, follow_up_on)`, created in migration V2.

## 6. Security

- **Stateless JWT**: no server session; each request carries
  `Authorization: Bearer <token>`. Scales horizontally, fits a SPA client.
- **Spring Security resource server** validates tokens (signature, `exp`,
  `iss`) with its own filter, instead of a hand-written filter: less custom
  security code to get wrong.
- **HS256 with one secret**: the same application issues and verifies tokens.
  RS256 (private/public key pair) would be the choice with several services.
- **Secret never committed**: read from `JWT_SECRET` (environment or a local,
  git-ignored `backend/.env`). Typed `@ConfigurationProperties` validated at
  startup: the app refuses to start with a missing or too short key.
- **Token content**: `sub` = user id (stable), `email`, `iat`, `exp`, `iss`.
  JWTs are signed, not encrypted: nothing secret goes inside.
- **Deny by default**: `anyRequest().authenticated()`; only register, login and
  health are public, so a new route is protected unless explicitly opened.
- **CSRF disabled** on purpose: CSRF abuses cookies sent automatically by the
  browser; a bearer token is added explicitly by the client.
- **Passwords**: BCrypt through `DelegatingPasswordEncoder` (`{bcrypt}` prefix
  allows a future algorithm change). 8-72 characters: BCrypt ignores bytes
  beyond 72. Request DTOs mask passwords in `toString()`.
- **Login delegated to `DaoAuthenticationProvider`**, which also hashes a dummy
  password for unknown emails (timing-attack protection). Wrong password and
  unknown email return the same 401.
- **Registration returns 409 for a used email**, accepted trade-off: it reveals
  that the account exists. The concurrent-insert race is caught via the unique
  constraint. Registration logs the user in directly (returns a token).
- **401 in ProblemDetail format** from a custom entry point: authentication
  fails in a servlet filter, before controllers, so `@RestControllerAdvice`
  never sees it.
- **`CurrentUserProvider` paid off**: switching from the temporary header to
  JWT changed one implementation class; controllers and services were untouched.
- **Known limits** (out of scope for V1): no refresh token (one-hour expiry,
  then log in again), no server-side logout or revocation (the client drops
  the token), no rate limiting on login.
